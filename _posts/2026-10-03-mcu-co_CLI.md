## Introduction

In this post we will go over `mcu-co-cli`, the command-line tool that ships with the mcu-co SDK. It is built on top of the mcuco library we covered in [P8]({% post_url 2026-09-19-mcu-co_Shared_Library_Linux %}).

So why have a CLI at all? Because sometimes you just want to flip a pin. During bring-up you want to check the link, drive an output or read an input without writing, compiling and running a C program each time. The CLI lets you do that straight from the shell, and since it reports success through its exit code, you can drop it into scripts too.

The source for the CLI is [here](https://github.com/Causality-Labs/mcu-co_sdk/tree/main/cli).

#### What the tool looks like

Every command has the same shape: a subsystem, a verb, then the values.

{% highlight bash linenos %}
mcu-co-cli <subsystem> <verb> <values...>
{% endhighlight %}

A pin is written as its port and number, so pin 5 on port A is `A 5`. Here is a short session:

{% highlight bash linenos %}
mcu-co-cli mcu probe                          # check the link
mcu-co-cli gpio cfg output A 5                # make A5 an output
mcu-co-cli gpio set high A 5                  # drive it high
mcu-co-cli gpio toggle A 5                    # flip it, prints the new level
mcu-co-cli timer cfg 1000 0                   # timer 0 at 1 kHz
mcu-co-cli pwm cfg active-high A 1            # claim A1 for PWM
mcu-co-cli pwm set 25 A 1                     # 25% duty
mcu-co-cli irq cfg falling C 13               # arm a falling-edge trigger on C13
mcu-co-cli irq bind falling C 13 toggle A 5   # each falling edge on C13 toggles A5
{% endhighlight %}


## Parsing the options

The CLI takes three options:

- `-d, --device <path>`: the serial port, `/dev/ttyACM0` by default.
- `-t, --timeout <ms>`: how long to wait for a reply, 1000 ms by default.
- `-h, --help`: prints every command and its arguments.

The parsed options are stored in a `config_t`:

{% highlight c linenos %}
typedef struct
{
    char *device_path;
    uint16_t timeout;
    bool help;
} config_t;
{% endhighlight %}

`parse_config()` in `main.c` fills it in using `getopt_long`, the standard way to parse options in C on Linux. It starts by setting the defaults, then overrides them with whatever options were passed:

{% highlight c linenos %}
static int parse_config(int argc, char **argv, config_t *config)
{
    static const struct option longopts[] = {
        {"device", required_argument, NULL, 'd'},
        {"timeout", required_argument, NULL, 't'},
        {"help", no_argument, NULL, 'h'},
        {NULL, 0, NULL, 0},
    };

    static const char *const shortopts = "d:t:h";

    (void)memset(config, 0, sizeof(config_t));
    config->timeout     = 1000U;
    config->device_path = "/dev/ttyACM0";

    int opti = 0;
    int optc = 0;

    for (;;)
    {
        optc = getopt_long(argc, argv, shortopts, longopts, &opti);
        if (optc < 0)
        {
            break;
        }

        switch (optc)
        {
        case 'd':
            config->device_path = optarg;
            break;

        case 't':
            if (parse_timeout(optarg, &config->timeout) != 0)
            {
                fprintf(stderr, "mcu-co-cli: bad timeout '%s' (%lu-%lu ms)\n", optarg, TIMEOUT_MIN_MS, TIMEOUT_MAX_MS);
                return -1;
            }
            break;

        case 'h':
            config->help = true;
            break;

        default:
            return -1;
        }
    }

    return optind;
}
{% endhighlight %}

`getopt_long` moves the options to the front of `argv`, so they can go anywhere in the command. Both of these work:

{% highlight bash linenos %}
mcu-co-cli -d /dev/ttyUSB0 gpio get C 13
mcu-co-cli gpio get C 13 -d /dev/ttyUSB0
{% endhighlight %}

Once the options are parsed, `optind` points at the first word that is not an option, which is where the command starts. `parse_config()` returns it so `main()` knows where to begin reading the subsystem and verb.


## The command table

Every command the CLI understands is described by a `command_t`, defined in `commands.h`:

{% highlight c linenos %}
typedef struct
{
    const char *subsystem;
    const char *verb;
    int value_count;
    word_kind_t values[MAX_VALUE_WORDS];
    mcu_status_t (*run)(mcuco_t *mcu, const mcuco_args_t *mcuco_args);
    const char *usage;
    const char *summary;
} command_t;
{% endhighlight %}

- `subsystem` and `verb`: the first two words of the command, e.g. `gpio` and `set`.
- `value_count` and `values`: how many values follow, and what kind each one is.
- `run`: the function that runs the command.
- `usage` and `summary`: the text printed by `--help`.

All the commands live in one table in `commands.c`. Here are a few rows:

{% highlight c linenos %}
static const command_t commands[] = {
    {"mcu",  "probe", 0, {WORD_NONE},                           run_probe,    "",                     "check the link"},
    {"gpio", "cfg",   3, {WORD_DIRECTION, WORD_PORT, WORD_PIN}, run_gpio_cfg, "<input|output> <pin>", "set a pin's direction"},
    {"gpio", "set",   3, {WORD_LEVEL, WORD_PORT, WORD_PIN},     run_gpio_set, "<low|high> <pin>",     "drive an output pin"},
    {"pwm",  "set",   3, {WORD_DUTY, WORD_PORT, WORD_PIN},      run_pwm_set,  "<0-100> <pin>",        "percent, then the pin"},
    /* ... */
};
{% endhighlight %}

If this looks familiar, it is the same idea as the command dispatcher from [P5]({% post_url 2026-09-09-mcu-co_Command_Dispatcher %}): a table of function pointers instead of a giant switch statement. The difference is that this one runs on the host, not the MCU. To find a command, the CLI looks up the row whose subsystem and verb match the first two words, then calls its `run` function.

#### Describing the values with word kinds

The `values` array is what makes the table work. It lists the kind of each value word, in the order the user types them:

{% highlight c linenos %}
typedef enum
{
    WORD_NONE = 0,
    WORD_DIRECTION,
    WORD_LEVEL,
    WORD_PORT,
    WORD_PIN,
    WORD_FREQUENCY,
    WORD_TIMER,
    WORD_POLARITY,
    WORD_DUTY,
    WORD_EDGE,
    WORD_BIND_EDGE,
    WORD_ACTION,
    WORD_OUT_PORT,
    WORD_OUT_PIN,
} word_kind_t;
{% endhighlight %}

So the `gpio cfg` row says "this command takes a direction, a port and a pin", and the parser takes care of the rest. No command needs its own parsing code.

Two of these are worth pointing out:

- `WORD_BIND_EDGE` is the same as `WORD_EDGE`, except it refuses `off`. Arming a trigger with `off` makes sense, but binding an action to an edge that never fires does not.
- `WORD_OUT_PORT` and `WORD_OUT_PIN` exist because `irq bind` takes two pins: the one that triggers and the one that gets driven. Giving them their own kinds stores them in separate fields, so they can't overwrite each other.


## Turning words into arguments

Once the options are out of the way, `main()` hands the remaining words to `args_parse_mcuco()`:

{% highlight c linenos %}
int args_parse_mcuco(int word_count, char **words, const command_t **command, mcuco_args_t *mcuco_args)
{
    if (word_count < FIRST_VALUE_WORD)
    {
        return -1;
    }

    const command_t *found = mcuco_find_command(words[SUBSYSTEM_WORD], words[VERB_WORD]);
    if (found == NULL)
    {
        return -1;
    }

    int expected_word_count = FIRST_VALUE_WORD + found->value_count;
    if (word_count != expected_word_count)
    {
        return -1;
    }

    for (int value_index = 0; value_index < found->value_count; value_index++)
    {
        if (parse_value(found->values[value_index], words[FIRST_VALUE_WORD + value_index], mcuco_args) != 0)
        {
            return -1;
        }
    }

    *command = found;
    return 0;
}
{% endhighlight %}

It does three things:

1. Finds the row whose subsystem and verb match the first two words.
2. Checks that the number of words is right for that row.
3. Parses each value word according to its kind, filling in an `mcuco_args_t`.

`*command` is only set at the very end, so a command that fails to parse never gets run.

`parse_value()` is just a switch that sends each word kind to a small parser. Here are two of them:

{% highlight c linenos %}
static int parse_port(const char *word, port_t *port)
{
    if (word[0] < 'A' || word[0] > 'G' || word[1] != '\0')
    {
        return -1;
    }

    *port = (port_t)(word[0] - 'A');
    return 0;
}

static int parse_pin(const char *word, uint8_t *pin)
{
    /* strtoul would accept "-1" and wrap it, so require a digit first. */
    if (word[0] < '0' || word[0] > '9')
    {
        return -1;
    }

    char *end           = NULL;
    unsigned long value = strtoul(word, &end, 10);
    if (*end != '\0' || value > PIN_MAX)
    {
        return -1;
    }

    *pin = (uint8_t)value;
    return 0;
}
{% endhighlight %}

`parse_pin` checks for a digit before calling `strtoul`. That is because `strtoul` happily accepts `-1` and wraps it into a huge unsigned number. Checking `*end` makes sure the whole word was a number, so `5x` is rejected too.

All of this happens before the CLI touches the serial port. A typo is caught right away, without a round trip to the MCU.


## Running the command

Each `run` function is tiny, since all it does is call one library function with the parsed arguments:

{% highlight c linenos %}
static mcu_status_t run_gpio_set(mcuco_t *mcu, const mcuco_args_t *mcuco_args)
{
    return mcuco_gpio_set(mcu, mcuco_args->level, mcuco_args->port, mcuco_args->pin);
}
{% endhighlight %}

Commands that read something back also print it:

{% highlight c linenos %}
static mcu_status_t run_gpio_get(mcuco_t *mcu, const mcuco_args_t *mcuco_args)
{
    level_t level = LEVEL_LOW;

    mcu_status_t status = mcuco_gpio_get(mcu, mcuco_args->port, mcuco_args->pin, &level);
    if (status == MCUCO_STATUS_OK)
    {
        print_level(level);
    }

    return status;
}
{% endhighlight %}

Here is how `main()` puts it all together:

{% highlight c linenos %}
const command_t *command = NULL;
mcuco_args_t mcuco_args  = {0};
int word_count           = argc - word_index;
if (args_parse_mcuco(word_count, &argv[word_index], &command, &mcuco_args) != 0)
{
    fprintf(stderr, "mcu-co-cli: bad command\n");
    fprintf(stderr, "try 'mcu-co-cli --help'\n");
    return 1;
}

mcuco_t *mcu = mcuco_open(config.device_path, config.timeout);
if (mcu == NULL)
{
    fprintf(stderr, "mcu-co-cli: could not open mcuco device\n");
    return 1;
}

mcu_status_t status = mcuco_run_command(mcu, command, &mcuco_args);
fprintf(stderr, "%s\n", mcuco_strerror(status));

mcuco_close(mcu);

return (status == MCUCO_STATUS_OK) ? 0 : 1;
{% endhighlight %}

Parse the command, open the port, run the command, print the status, close the port. Notice that `mcuco_strerror` from the library does the work of turning the status into a message.

#### Playing nicely with scripts

The CLI follows three simple rules so it works well in scripts:

- Values go to **stdout**.
- Status messages go to **stderr**.
- The exit code is `0` on success and `1` on failure.

That means you can capture a value and check for errors the usual way:

{% highlight bash linenos %}
if level=$(mcu-co-cli gpio get C 13 2>/dev/null); then
    echo "C13 is ${level}"
else
    echo "could not read C13"
fi
{% endhighlight %}


## Help text for free

`mcuco_print_commands()` walks the same command table and prints each row's `usage` and `summary`. So adding a command to the table also documents it. Here is part of what `mcu-co-cli --help` prints:

{% highlight text %}
usage: mcu-co-cli <subsystem> <verb> <values...> [--options anywhere]

  mcu    probe                                 check the link
         reset                                 reboot the MCU

  gpio   cfg      <input|output> <pin>         set a pin's direction
         set      <low|high> <pin>             drive an output pin
         get      <pin>                        -> low | high
         toggle   <pin>                        -> the level after the flip

  timer  cfg      <1-1000000> <0-2>            Hz, then which timer
         get      <0-2>                        -> achieved Hz
         release  <0-2>                        stop it, freezing its pins

  pwm    cfg      <polarity> <pin>             claim a pin, silent at 0%
         set      <0-100> <pin>                percent, then the pin
         get      <pin>                        -> percent, one decimal
         release  <pin>                        free one pin

  irq    cfg      <edge> <pin>                 arm or disarm a trigger
         bind     <edge> <pin> <action> <pin>  drive one pin from another
         unbind   <pin>                        drop the action, stay armed
{% endhighlight %}

## Conclusion

The CLI is a table, a parser and a set of one-line handlers on top of the mcuco library. Adding a new command takes one `run` function and one row in the table, and the parser, help text and error handling all come with it.
