mcu-co SDK (September 2026- October 2026)

Linux SDK for mcu-co, a C shared library, CLI tool and example programs that let a Linux host drive the MCU co-processor over a serial link.

Overview

mcu-co pairs a Linux host with a microcontroller that handles the timing-critical work, like PWM generation, interrupt handling and I/O expansion. The host stays free for high-level application logic, and the MCU gives it deterministic pin behavior without needing a real-time kernel. The microcontroller side is covered on the mcu-co firmware page.

This page covers the Linux side of the project: the mcu-co SDK. It is made up of a shared library written in C (libmcuco.so), a CLI tool (mcu-co-cli) and a set of example programs. Applications call the library and never have to deal with the serial port or the command protocol themselves. The SDK is also packaged as a Yocto recipe, so it can be built into any custom embedded Linux image.

This page is a high-level overview. The details are covered in their own posts: how to create a shared library in Linux and building the CLI. Here is a link to all of these posts.

Source code for the SDK can be found here: mcu-co SDK, and the Yocto recipe here: meta-causality-labs.

Software

The SDK is written in C11 and built with CMake, so it can be cross-compiled for any Linux host. It is made up of the following parts:

Shared Library (libmcuco.so): Gives applications a small C API for GPIO, interrupts and PWM. It owns the serial link and the command protocol, so a program just calls functions like mcuco_gpio_set() and gets a status code back. The full design is covered in how to create a shared library in Linux.

CLI (mcu-co-cli): Exposes every library operation from the shell, which makes it useful for bring-up, testing and scripting. The full design is covered in building the CLI.

Example Programs: Small programs that show the library in use: blink, pwm_frequency, pwm_breathe and irq_bind.

Yocto Recipe

The SDK is also packaged as a recipe in my meta-causality-labs Yocto layer. Anyone building a custom embedded Linux image can add the layer and get the library, CLI and examples cross-compiled for their target. If you are new to Yocto, my posts on creating a new meta layer and writing a recipe cover the background.

The recipe is short, because the SDK's own CMake build does most of the work:

  • It fetches the SDK from GitHub at a pinned commit, so every build uses the same source.
  • It inherits cmake, so Yocto runs the SDK's own build with the target's cross toolchain. Unit tests are turned off for the target build.
  • The examples go in their own package, mcu-co-examples, so an image can ship the library and CLI without them.
  • The examples are installed with an mcu-co- prefix, because the SDK builds them but doesn't install them, and names like blink are too generic for /usr/bin.

Conclusion

The SDK completes the mcu-co project. A Linux application can now drive the co-processor through a small C library, a CLI covers the same operations from the shell, and the Yocto recipe lets the whole thing drop into a custom embedded Linux image. Together with the firmware, mcu-co gives a Linux host PWM, interrupt handling and I/O expansion with deterministic timing, without needing a real-time kernel.
